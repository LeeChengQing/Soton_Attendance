# 368FK 商品与手机提醒密钥激活设计

> 本设计根据用户确认的商品结构与密钥兑换流程编写。它替换 `2026-10-01-manual-activation-design.md` 中的付款编号、激活申请和管理员逐单审核流程；保留服务端强制检查手机提醒授权、本机自动打卡独立运行及现有用户数据不删除的要求。

## 目标

在 Soton Auto-Check 设置页增加 368FK 套餐入口与一次性密钥兑换。用户在 368FK 自动发货购买对应套餐后，取得唯一密钥并在插件中兑换；Supabase 将密钥绑定到当前设备并授予该学期的手机提醒权限。收款与商品库存仍由 368FK 管理，第一版不接 368FK 支付 API 或订单 webhook。

## 已确认的商品规则

- 保留现有 ¥10 插件商品，不修改价格或内容。
- 新建 ¥12 首学期套餐（`bundle`）和 ¥5/学期手机提醒续期商品（`phone_notifications`）。
- ¥12 套餐商品包含插件使用权和首学期手机提醒；续期商品只延长手机提醒权限。本功能只在服务端限制手机提醒，不新增本机自动打卡的付费锁。
- 每学期为各商品生成一批密钥；生成批次时指定该学期的固定截止日期。
- 商品页还未创建时，设置页按钮打开卖家店铺页 `https://shop.368fk.cn/shop/CFI5VKXO`。拿到两个新商品的详情页链接后，可以分别改为直达商品页。
- 续期密钥只授予到该密钥批次指定的学期截止日；如果当前授权已经晚于这个截止日，兑换不会再增加时长，同一学期的密钥不会叠加。
- 368FK 当前商品页显示“自动发货”和卡密寄售说明；库存配置按每笔订单发放一条密钥处理。将密钥库存导入商家后台前，管理员需确认该商品配置确实会逐单发放不同库存卡密。

## 密钥发放与兑换

1. 使用 Node.js 内置密码学库生成高熵的一次性密钥批次。生成结果分成两份：可供 368FK 自动发货库存使用的明文密钥清单，以及只含 SHA-256 哈希、套餐和学期截止日的 Supabase 导入清单。
2. 管理员将明文清单装入相应 368FK 商品的自动发货库存，并将哈希清单导入 Supabase。明文清单不提交到 Git；扩展中不保存任何后台密钥。
3. 设置页展示套餐价格、购买入口、当前授权与到期日，并提供密钥输入和激活按钮。密钥只能绑定到携带有效设备 token 的当前设备；客户端不能传设备 ID、套餐或到期时间。
4. `device-api` 规范化用户输入并计算哈希，通过 Postgres 事务函数原子兑换一个未使用密钥。事务将密钥标记为已兑换并创建或续期设备的唯一手机提醒授权，避免并发或重复兑换。
5. 密钥中的套餐与学期截止日来自服务端记录。新授权从兑换时生效；已有授权续期时保留当前权限，并将到期日更新为当前到期日与密钥截止日两者中的较晚值。截止日已过的密钥不可兑换。
6. 被拒绝、撤销、过期或已兑换的密钥不能发放权限。兑换成功后，密钥记录保存兑换设备与时间以便管理员审计。

## 数据模型

### `activation_keys`

- 每个密钥一行，数据库只保存 `key_hash`，并设唯一约束。
- `plan` 仅允许 `bundle` 或 `phone_notifications`。
- `term_expires_at` 保存密钥对应学期的截止时间。
- `status` 仅允许 `available`、`redeemed`、`revoked`。
- `redeemed_device_id`、`redeemed_at` 记录一次性兑换结果；以及 `created_at`、`note`。
- 密钥对应的学期截止时间不得早于兑换时间。

### `entitlements`

- `device_id` 作为主键，每个设备最多一条当前手机提醒授权。
- 保存 `plan`、`status`、`phone_notifications`、`starts_at`、`expires_at`、`source`、`note`、`created_at`、`updated_at`；`status` 约束为 `pending`、`active`、`expired`、`revoked`。
- `source` 对由商店密钥兑换的授权固定为 `shop`。
- 续期更新当前记录，不创建重复权限。管理员仍可在 Supabase 手动撤销授权。

### 原有数据访问边界

- 两张新表启用 RLS，拒绝 `anon` 和 `authenticated` 直接读写。
- `device-api` 使用 Supabase 环境中的 service-role 客户端访问；扩展只持有设备 token。
- 兑换事务函数仅授权给后端 service role 调用。

## API 与通知

在现有 `device-api` 中增加：

- `entitlement-status`：使用 bearer token 返回当前设备授权的套餐、状态与有效期。
- `redeem-activation-key`：使用 bearer token 接收密钥；成功时服务端兑换，失败时返回无效、已使用、已撤销或已过期的明确错误。

`notification-worker` 在查 ntfy 主题或发请求前，必须确认同设备的授权为 active、`phone_notifications = true`、`starts_at <= now` 且 `expires_at > now`。无有效授权时不发送，保持 `sent_at` 为空，将 `last_error` 设为 `subscription_required` 并设置 `discarded_at`，保留记录但从待发送队列移除，避免旧未授权通知阻塞后续队列。已授权设备继续使用原 ntfy 主题和通知内容。

本机自动打卡不读取手机提醒授权，不因缺少、撤销或到期的提醒权限而停止。课程表、Forms 绑定、打卡记录、ntfy 配置均保留。

## 插件设置页

- 保留现有 ntfy 订阅主题显示。
- 展示 ¥12 首学期套餐和 ¥5/学期续期说明；新订阅按钮打开卖家店铺页，取得新商品 URL 后可分别切换到详情页。现有 ¥10 商品继续保留在商店，但不作为手机提醒订阅入口。
- 提供密钥输入框、“激活”与“刷新授权”按钮。
- 显示当前套餐、授权状态、学期截止日期，以及激活失败原因。
- 不再要求付款编号、联系方式或设备查找码。
- 设置页的本地状态不能改变服务端授权；仅成功兑换密钥或管理员修改授权记录才会允许服务端通知。

## 运维

- 先对某学期生成密钥批次，再分别将明文库存导入对应 368FK 商品、将哈希记录导入 Supabase。
- 新增套餐商品与密钥库存由店主管理；实现代码不创建或修改 368FK 商品，也不登录商家后台。
- 商城费率尚未从公开商品页确认；该费用信息不进入扩展逻辑。

## 验收标准

- 设置页显示 ¥12 首学期套餐与 ¥5/学期续期入口，购买入口能打开卖家店铺页；现有 ¥10 商店商品未被代码修改或当作提醒订阅入口。
- 两种套餐批次均能提供可自动发货的唯一明文密钥和对应的哈希导入数据。
- 有效密钥只能兑换一次，并绑定到发起兑换的设备；猜测、重复提交、撤销或过期密钥不能激活。
- 成功兑换后，设置页刷新显示授权套餐和截止日期；合法有效期内的测试提醒可由 worker 投递。
- 未授权、未开始、已撤销或过期授权的 outbox 项不会发送，记录 `last_error=subscription_required`、保留空 `sent_at` 并标记丢弃；100 条丢弃记录不会阻塞后续已授权通知。
- 密钥兑换或提醒授权状态不会修改本机课程、Forms 绑定、打卡记录或自动打卡安排。
- 扩展包不包含明文密钥库存、service-role key 或其他后台凭据。
