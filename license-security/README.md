# Two-project licensing and payment webhooks

This is a self-contained implementation. China is the only database for licenses, orders, device bindings, expiry and consumption quotas. The Global project's proxy performs a China lookup on every request. These files are not wired into the existing attendance extension or its phone-notification licensing system, and no remote project has been modified.

## Step 1 — China SQL

Run [china/schema.sql](china/schema.sql) once in the intended Auth project's SQL editor, or incorporate it into that project's migration workflow. The script is transactional and deliberately fails if these tables already exist; review existing schemas instead of silently replacing them.

The core table includes the requested fields:

```sql
key uuid primary key default gen_random_uuid(),
source text not null default 'card_network',
max_devices integer not null default 1,
bound_devices text[] not null default '{}'::text[],
is_active boolean not null default true
```

The full SQL adds expiry, constraints, order/payment uniqueness, default-deny RLS, explicit service-role grants and two service-only RPCs. `bind_license_device` locks the license row before checking/adding a device. `consume_license_request` revalidates and reserves quota under the same kind of lock. Browser clients cannot read license inventories or modify license rows/RPCs.

Card-network inventory: securely batch-import UUID v4 keys into `license_keys` with `source = 'card_network'`. Omit payment-order/reference columns. Supply `max_devices`, `expires_at` and quotas from the purchased plan; omitted quotas default to 30 requests per minute and 1000 per UTC day. UUIDs are generated by PostgreSQL `gen_random_uuid()` or server-side `crypto.randomUUID()`; use high-entropy inventory and do not publish it.

## Step 2 — Global website webhooks writing directly to China

Full implementation: [webhooks.js](../lib/license-security/website/webhooks.js), server configuration: [runtime.js](../lib/license-security/website/runtime.js). The canonical website modules and their shared helper now live under `lib/license-security/`; the old `website/` imports remain compatibility entry points. The handlers accept standard `Request` objects and return `Response` objects. Use Node 22 or later. No service credential belongs in browser code or a `NEXT_PUBLIC_` variable. Install the root package dependencies with `npm ci`.

Before redirecting a buyer to payment, the authenticated website checkout server must create the provider's session/bill and persist a `payment_orders` row in China with:

- `id`: a server-generated UUID v4. For ToyyibPay pass this exact value as `billExternalReferenceNo` when creating the bill.
- `buyer_id`: your authenticated website user's stable identifier.
- `source`: `stripe` or `toyyibpay`; `provider_order_id`: Stripe Checkout Session ID or ToyyibPay BillCode returned by the provider API.
- `amount_minor`, lowercase `currency`, `max_devices`, `expires_at`: immutable values from your server's product catalog. Never accept device limits/prices from the callback or a buyer-supplied request.

Persist the order before exposing the provider redirect URL. Use fixed-price, single-payment ToyyibPay bills; charge fees to the merchant so the verified amount equals the recorded price. For Stripe this implementation covers one-time Checkout payments; do not use subscription mode. If applying discounts/taxes, record the final expected total/currency before redirecting.

Next.js App Router integration: keep `lib/license-security/website/` and `lib/license-security/shared/` together. The route files below are included in this repository and expose `POST /api/webhook/stripe` and `POST /api/webhook/toyyibpay`. Relative imports work without configuring an `@/` alias. Run these files in your Next.js website; this attendance extension repository does not itself include a Next.js application runtime.

```js
// app/api/webhook/stripe/route.ts
import { paymentWebhooks } from '../../../../lib/license-security/website/runtime.js';
export const runtime = 'nodejs';
export const POST = paymentWebhooks.stripe;
```

```js
// app/api/webhook/toyyibpay/route.ts
import { paymentWebhooks } from '../../../../lib/license-security/website/runtime.js';
export const runtime = 'nodejs';
export const POST = paymentWebhooks.toyyibpay;
```

Website server environment:

```text
CHINA_SUPABASE_URL
CHINA_SUPABASE_SERVICE_ROLE_KEY
STRIPE_SECRET_KEY
STRIPE_WEBHOOK_SECRET
STRIPE_LIVE_MODE              # literal true for live, false for test
TOYYIBPAY_USER_SECRET_KEY
TOYYIBPAY_SANDBOX             # literal true for dev.toyyibpay.com, false for live
```

Register Stripe events `checkout.session.completed` and `checkout.session.async_payment_succeeded`; the handler issues only when `payment_status` is `paid`. It verifies the untouched request body with Stripe's SDK before parsing the event. Align the webhook endpoint's event API version with the installed Stripe SDK. [Stripe webhook documentation](https://docs.stripe.com/webhooks).

ToyyibPay must use the server-side callback URL, not the browser return URL. The handler verifies the provider's documented MD5 callback hash with a constant-time comparison, checks the known bill/order/amount, and retrieves successful transactions from ToyyibPay. It matches the order's external reference, exact amount and authoritative invoice number. Missing/ambiguous provider evidence fails closed. The standard URL-encoded callback is supported; multipart callbacks are deliberately rejected. [ToyyibPay API reference](https://toyyibpay.com/apireference/).

Both handlers insert directly into China with a random UUID and `ON CONFLICT (payment_order_id) DO NOTHING`. Retries cannot issue a second license, reactivate a revoked license or wipe bindings. A unique provider payment reference also prevents reusing one payment across multiple orders. Network/database failures return non-2xx so the provider can retry. Monitor unresolved callback failures and reconcile payments against providers; do not assume ToyyibPay offers Stripe's retry guarantees.

Webhook responses acknowledge receipt without exposing the license. The existing authenticated website fulfillment route can join a buyer's `payment_orders.id` to `license_keys.payment_order_id` using a server client, verify `buyer_id` against the signed-in user, and display the issued key only to that buyer. No public key-by-order-ID endpoint is provided. Refunds/chargebacks must revoke `is_active` through your billing workflow; this implementation does not define a refund/subscription policy.

## Steps 3 and 4 — Extension clients, identity, activation

Full frontend: [frontend/license.js](frontend/license.js). Build it locally:

```powershell
Set-Location C:\自动打卡系统\license-security
npm ci
npm run build
```

Ship `dist/license-client.js` in the extension. Add Chrome `storage` permission and HTTPS host permissions for both actual project origins. Keep the background service worker's `type` as `module` when importing ES modules. No CDN scripts are needed.

Initialize from your existing trusted extension configuration (only project URLs and publishable/legacy anon keys):

```js
import { createLicenseFrontend } from './license-client.js';

const {
  supabaseAuth,
  supabaseBusiness,
  getDeviceId,
  activateLicense,
  callChatGPT,
} = createLicenseFrontend(extensionPublicConfig);

// extensionPublicConfig contains:
// chinaUrl, chinaPublishableKey, businessUrl, businessPublishableKey.
// Integrate activateLicense(input.value) into your trusted activation UI;
// callChatGPT(messages) invokes the Global function with stored credentials.
```

`getDeviceId()` uses `crypto.randomUUID()`, `chrome.storage.local`, and a cross-context Web Lock so simultaneous popup/worker initialization cannot create different IDs. `setAccessLevel(TRUSTED_CONTEXTS)` prevents content scripts from reading local storage; it applies to the entire local storage area, so integrations must send permitted content-script data through validated background messages. Do not expose activation/proxy methods through unrestricted content-script or external-message handlers.

Activation intentionally calls the China `activate-license` Edge Function instead of exposing table SELECT/UPDATE to the browser. The function performs the requested active-key check and existing-device/available-slot/full-device branches atomically. Success saves the license locally; a failed new activation preserves the previous license. Browser-side checks are convenience only: local ZIP edits cannot grant service access.

## Step 5 — Global Edge proxy

Complete handler: [business/functions/chatgpt-proxy/chatgpt-proxy.ts](business/functions/chatgpt-proxy/chatgpt-proxy.ts); deployable entry point: [business/functions/chatgpt-proxy/index.ts](business/functions/chatgpt-proxy/index.ts). China activation handler/entry point are in [china/functions/activate-license](china/functions/activate-license).

The proxy extracts `x-license-key` and `x-device-id`, uses a server-only China client, checks active/expiry/device membership, validates the messages, then revalidates while atomically reserving quota. Missing/invalid/revoked/expired/unbound credentials return 403; China outages return 503 without contacting OpenAI; quota exhaustion returns 429. Only an authorized request reaches the fixed OpenAI URL. The model, non-streaming mode and 1024 completion-token cap are owned by the server. Choose an `OPENAI_MODEL` that supports the Chat Completions API and `max_completion_tokens`. [OpenAI Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

Requests/upstream bodies have byte limits and deadlines. Raw license headers and China credentials are never forwarded to OpenAI or included in error logs. Usage quota charges accepted requests even when OpenAI later fails; no automatic AI retries or quota refunds are performed. Daily quotas reset at UTC midnight.

Global Edge secrets:

```text
CHINA_SUPABASE_URL
CHINA_SUPABASE_SERVICE_ROLE_KEY
OPENAI_API_KEY
OPENAI_MODEL
ALLOWED_ORIGINS
```

China activation Edge secrets: `ALLOWED_ORIGINS`; the China function uses its built-in `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. `ALLOWED_ORIGINS` is a comma-separated list of your exact `chrome-extension://` origins (and HTTPS application origins if needed). A leaked unpacked ZIP may receive a different extension ID. CORS is not caller authentication and is not the piracy boundary.

Both function configs use `verify_jwt = false` because these handlers authenticate custom license/device credentials, rather than Supabase user sessions. Publishable keys are public application identifiers. [Supabase function authorization documentation](https://supabase.com/docs/guides/functions/auth).

Run `npm run prepare:deploy` to stage two standard, separate CLI project layouts in `dist/china` and `dist/business`. Each contains `supabase/config.toml`, function entry points, shared helpers and a pinned Deno lockfile. Deploy `activate-license` to the China project and `chatgpt-proxy` to the Global project; the respective config keeps the custom-auth gateway setting. Apply the SQL only to China. Set secrets in each intended project's dashboard or secrets CLI; never commit a populated secrets file.

## Verification and security boundary

```powershell
npm test
npm run test:edge
npm run check:edge
npm run build
npm run prepare:deploy
```

SQL tests use an actual embedded PostgreSQL engine with simulated Supabase roles. Frontend, webhook and Edge tests replace only external browser/network boundaries. They cover device identity races, activation/device limits, grants/RLS, quotas, expiry/revocation, webhook signature/amount/order checks, retries, provider evidence and upstream rejection paths. This is local verification, not evidence of successful live deployment. Before releasing, run real Stripe/ToyyibPay sandbox callbacks and multi-connection activation/quota tests against isolated Supabase projects, then verify the deployed anon/RPC permissions and gateway settings.

A persistent UUID is an installation identifier, not hardware attestation. Anyone who copies both the valid license key and a bound device ID can replay that identity. Account authentication and per-device key-pair challenge signing can make sharing harder; an untrusted browser cannot guarantee non-exportable physical-device identity. Rate-limit activation attempts at your trusted ingress using the platform's real peer IP, and set provider/project spend limits appropriate to the plans. This protects your paid Global service; code/features that run entirely locally remain editable in a leaked ZIP.

No actual project endpoints or secrets were supplied for this new two-project system. Configuration must come from the intended projects; existing workspace project IDs are not silently reused.
